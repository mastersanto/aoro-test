## Context

The user invoked `/spec` (SDD step 1) for the Aoro test assignment: **"Create a Polymarket widget on a single page. The widget should allow a user to search markets, and the user can place a bet on a market. For a recommended bonus, connect your widget to AI to get AI-assisted predictions."**

The repo holds only the committed SDD harness (constitution, templates, slash commands) — no feature specs exist. This step produces the WHAT/WHY spec for feature 001; no application code and no technology choices (those come in `/plan-feature`).

Scope decisions resolved with the user in plan mode:

1. **Single page only** — no embeddable/third-party version; embedding is explicitly out-of-scope (matches the assignment).
2. **Both money modes in v1** — real betting plus a clearly-labeled demo/practice mode (real market data, simulated balance) so a reviewer without a funded wallet can exercise the full bet flow.
3. **Wallet: user's own wallet** — user connects an existing wallet (USDC on Polygon) and signs each bet; no in-widget wallet creation.
4. **Geo policy: read-only degrade** — restricted regions can browse and use AI assistance; betting disabled with an explanation (constitution Art. V).
5. **AI assistance is framed as the assignment's "recommended bonus"** — core is search + bet; the spec marks priorities accordingly. Provider (Claude API, server-side) is already settled by the committed harness.

### `specs/001-polymarket-widget/spec.md` (from `specs/templates/spec-template.md`)

- **Why** — the assignment, plus one paragraph: betting on Polymarket requires navigating the full exchange; the widget compresses search → choose → bet into one page, with AI help for the undecided.
- **User stories with acceptance criteria** (citing constitution articles where they bind), priority-tagged **core** / **bonus**:
  - US-1 *(core)* Search and browse markets — live markets with title, outcomes, current prices, volume, end date; keyword search/filter; works with no wallet and no sign-in.
  - US-2 *(core)* Place a real bet — pick market/outcome/amount, see estimated payout, connect own wallet, explicit confirmation showing market/outcome/amount/price/payout (Art. II), signed client-side (Art. III); clear success (position shown) and failure states.
  - US-3 *(core)* Demo mode — toggle to practice with real market data and a simulated per-session balance; unmistakably labeled demo everywhere a bet-like action appears; no wallet needed; same flow as US-2 so it exercises the real UX.
  - US-4 *(bonus, per assignment)* AI-assisted predictions — user describes their interest, gets suggestions referencing real open markets with reasoning and current prices; "not financial advice" disclaimer visible (Art. V); suggestions only pre-fill the bet form, never trigger a bet (Art. II).
  - US-5 Geo read-only degrade — restricted regions get browse + AI only, betting controls disabled with an explanation (Art. V).
- **Out of scope (v1)** — embedding on third-party sites (future feature if wanted); portfolio management/order history; selling or closing positions; limit orders (market-style buys only); user accounts or server-side user state; in-widget wallet creation/custody.

### 3. SDD gate enforcement hook

- `.claude/hooks/sdd-gate.sh` — PreToolUse hook script for Write|Edit. Reads the tool-call JSON from stdin (parse with `python3`), extracts `tool_input.file_path`, and: **allow** writes to `specs/**`, `.claude/**`, root-level `*.md`, `.env.example`, and paths outside the repo; for anything else (application code), **block with exit 2** and an explanatory message unless some `specs/*/tasks.md` contains a checked "Task list approved" box. Known simplification (fine for this project, noted in the script header): the check is repo-wide, not per-feature.
- `.claude/settings.json` — project settings (checked in) registering the hook under `hooks.PreToolUse` with matcher `Write|Edit`. Load the `update-config` skill at implementation time for the exact settings schema.
- Manual verification after wiring: attempt a Write to a fake app-code path (e.g. `src/probe.ts`) and confirm the hook blocks it; then confirm a Write inside `specs/` passes. Remove any probe artifacts.

### 4. `/sdd-status` command — `.claude/commands/sdd-status.md`

Reports, for every `specs/NNN-*/` directory: gate state (spec/plan/tasks approval boxes), open `[NEEDS CLARIFICATION]` count, tasks checked vs. total, and the next command to run. Read-only; ends by naming the single next action.

### 5. Priority tags in the spec template

`specs/templates/spec-template.md`: user stories gain a priority tag — `*(core)*`, `*(bonus)*`, or `*(stretch)*` — after the story name, with a one-line rule: core stories block release, bonus/stretch don't. (Spec 001 already uses this convention; this makes it the rule.)

### 6. CI structure lint — `.github/workflows/sdd-lint.yml` + `scripts/sdd-lint.sh`

GitHub Action on push/PR to main running a small shell script that validates SDD invariants and fails the build on violation:
- every `specs/NNN-*/` contains `spec.md`, `plan.md`, `tasks.md`;
- approvals are ordered: plan approved ⇒ spec approved; tasks approved ⇒ plan approved;
- an approved spec contains no `[NEEDS CLARIFICATION]` markers.
The script also runs locally (`bash scripts/sdd-lint.sh`) so the hook-and-agent story has a CI counterpart. `/sdd-status` and the lint script must not double-implement parsing subtleties — keep both to simple greps of the same checkbox/marker strings the templates define.
